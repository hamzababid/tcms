## 2. Layering

`reporting` reads every module's tables through SQL (docs/03 §5) and owns metrics, queries, readiness, snapshots and reports. Releases and decisions stay in `workspace` (models exist); the decision service calls `reporting.readiness` through the API layer (workspace sits below reporting). Notifications stay in `platform`; renderers look up keys through SQL only.

## 3. Testing

- Unit: new metrics, rule evaluation per rule type (met / not met / undefined), defaults, merge per D1, CSV/XLSX cell escaping, digest time-zone window, notification renderers.
- Property tests: `ExecutionSummary` from SQL vs a Python oracle on random projects (superseded runs, NA, filters) (docs/08 §6.4); readiness vs oracle on the same fixtures.
- API: dashboards, reports (each filter), export sync and async (job runs inline in tests), decisions append-only, plan readiness, notifications list/read/count, preferences, authz matrix for every route, tenancy.
- E2E `m7.spec.ts` (axe): UJ-8 (Overview → readiness Not ready → finish runs → Ready → record Go → snapshot in the timeline), report export download, bell count and mark read, opt-out in Profile.
